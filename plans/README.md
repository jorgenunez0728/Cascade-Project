# Animation improvement plans

Generated by `/improve-animations` (standard effort, full audit) against
commit `ab531df`. Each plan is self-contained — see the individual files for
exact code, target values, and verification steps.

**All 11 plans have been implemented** (commit `78bae79`), in the order
below. `node --check` passed on every modified JS file and the rebuilt
bundle's largest inline script; CSS brace balance, zero remaining
`transition: all`, zero `scale(0)`, and zero leftover bounce cubic-beziers
were all verified before commit. Manual feel-checks in a browser are still
recommended per each plan's Verification section.

## Corrections made during vetting

Two findings from the initial audit were dropped after re-reading the actual
code (not just trusting the audit pass) — both were structurally unable to
have the effect originally claimed:

- **Cascade tooltip "scale from trigger"** — `cascadeShowTooltip()` never
  captures the trigger button's position; the popup is a centered overlay
  dialog, structurally identical to the app's other modal system.
  `AUDIT.md` explicitly exempts centered modals from the trigger-origin rule.
- **Cascade wizard `max-height` animation** — `renderCascadeTree()` does a
  full `innerHTML` rebuild of `#cascade-levels` on every selection
  (`js/cop15.js:480`), so every `.cascade-level` div is a brand-new DOM node
  each render. CSS `transition` (unlike `animation`) never plays on a
  freshly-inserted element — there's no prior state to interpolate from. The
  `transition: opacity 0.2s, max-height 0.3s ease` declaration is inert
  today; "fixing" its properties would have had zero real effect.

That leaves 11 plans instead of the original 13 findings.

## Recommended execution order

1. **Plan 001 first, always.** It's the only structural dependency — plans
   007 and 011 both reference `var(--ease-out)`, which 001 introduces.
2. **Plans 002–006 (all HIGH severity)** are independent of each other and of
   001 — safe to do in any order, or in parallel across different
   executors/sessions, since they each touch a different, non-overlapping
   area of the codebase (VIN field, Kanban search, Lab Overview, floor-plan
   drag, hover CSS).
3. **Plans 007–011 (MEDIUM severity)** — 007 and 011 need 001 done first;
   008, 009, 010 have no dependencies and can run any time.

A reasonable batch order: `001 → 002 → 003 → 004 → 005 → 006 → 007 → 008 → 009 → 010 → 011`.
